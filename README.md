# AsteroidProxOps
The code and data within this repository are done as part of the NASA Space Technology Graduate Research Opportunities (NSTGRO) fellowship:
Autonomous Landing and Proximity Operation Technology for Poorly-Characterized Small Bodies

The scripts in this repository will regenerate the data presented in the journal paper titled: 
Model Predictive Control Application and Cost Function Analysis for Time-of-Flight Free Asteroid Landings by Logan Feld, Dr. Joshua Lyzhoft, and Dr. Koki Ho

The goal of this work is to enable spacecraft to autonomously navigate the uncertain shape and gravity models around asteroids and other small bodies.

The main contributions to the project thus far are employing successive convex approximation (SCvx) to generate a reference trajectory about a polyhedral gravity model of the asteroid. This optimal reference trajectory can then be used to guide the spacecraft to a desired location on the asteroid through a model predictive control (MPC) algorithm that analyzes several time-of-flight free cost functions that penalize deviations from this safe, optimal trajectory to account for any uncertainties or errors in the gravity model. The uncertainties are navigated through the use of an Extended Kalman Filter (EKF).

## How to run:
```sh
conda create -n ENV_NAME python=3.9.13
conda activate ENV_NAME
pip install poetry OR conda install poetry
poetry install
```
Confirm environment by running the test scripts.
In the root directory, run:
```sh
pytest
```
## The output folder:
The output folder contains all the figures generated by the repository as they appear in the journal paper. Running the correct scripts (outlined below) without modification of any config files or source codes will regenerate the same figures as the journal paper. output/Monte_Carlo_outputs contains both the figures from the journal paper as well as numpy arrays that contain all the various collected statistics for the user to utilize as they see fit.

## The config files:
All the config files that the source code reads from are set up to regenerate all the results of the journal paper as is. The config files are found in the 'input' folder in the repository. Any of the config files can be edited except for the 'config_for_testing.ini' config file. This config file is specifically used for the pytest test scripts to ensure the repository is cloned properly, so it is recommended that this testing config file remains unchanged. config.ini, the other config file outside input/Monte_Carlo_configs, is the config file used to run a single MPC simulation (regenerating Fig 5-11, Table 4 from the journal paper) and can be edited freely. The 21 config files inside input/Monte_Carlo_configs contain the config parameters/values for all six cost functions and all three Landing Sites as well as three additional setup config files for each Landing Site (hence 3*(6+1) = 21 config files) for generating Monte Carlo statistics (regenerating Fig 12-13, Tables 7-9 from the journal paper) and can be edited freely.

The following section will go through what each line in a config file means explicitly. The values used for these parameters in the various simulations can be found in Tables 1, 2, 5, and 6 of the journal paper.

## Config file section - Simulation:

Tmin: min thrust of the spacecraft in Newtons (must be non-negative)

Tmax: max thrust of the spacecraft in Newtons (must be non-negative and higher than Tmin)

m_wet: wet mass of the spacecraft in kilograms (must be positive)

m_dry: dry mass of the spacecraft in kilograms (must be lower than m_wet and positive)

N: the number of subproblems/segments in the reference trajectory (SCvx) generation (must be at least 1)

dt: time step duration in seconds (must be greater than 0)

numstates: the number of states in the state vector (the paper uses 7 (3 position, 3 velocity, 1 mass) and it is not recommended changing this unless you update parts of the code accordingly)

m: number of controls in the control vector (the paper uses 4 (3 acceleration, 1 slack varable) and it is not recommended changing this unless you update parts of the code accordingly)

isp: specific impulse of thrusters in seconds (must be positive)

xi: true initial x position in meters in the asteroid body fixed frame

yi: true initial y position in meters in the asteroid body fixed frame

zi: true initial z position in meters in the asteroid body fixed frame

vxi: true initial x velocity in meters/sec in the asteroid body fixed frame

vyi: true initial y velocity in meters/sec in the asteroid body fixed frame

vzi: true initial z velocity in meters/sec in the asteroid body fixed frame

xhati: estimated initial x position in meters in the asteroid body fixed frame

yhati: estimated initial y position in meters in the asteroid body fixed frame

zhati: estimated initial z position in meters in the asteroid body fixed frame

vxhati: estimated initial x velocity in meters/sec in the asteroid body fixed frame

vyhati: estimated initial y velocity in meters/sec in the asteroid body fixed frame

vzhati: estimated initial z velocity in meters/sec in the asteroid body fixed frame

xf: target terminal x position in meters in the asteroid body fixed frame

yf: target terminal y position in meters in the asteroid body fixed frame

zf: target terminal z position in meters in the asteroid body fixed frame

overwrite_lli: Boolean value. If True, xf, yf, zf are used as the terminal position instead of landinglocindex (outlined later). If False, use landinglocindex to determine the target terminal position 

horizon: the number of steps in the MPC's prediction horizon. (must be an integer, at least 1)

Px: state covariance matrix diagonal value for x position in square meters (must be non-negative)

Py: state covariance matrix diagonal value for y position in square meters (must be non-negative)

Pz: state covariance matrix diagonal value for z position in square meters (must be non-negative)

Pvx: state covariance matrix diagonal value for x velocity in meters squared / sec squared (must be non-negative)

Pvy: state covariance matrix diagonal value for y velocity in meters squared / sec squared (must be non-negative)

Pvz: state covariance matrix diagonal value for z velocity in meters squared / sec squared (must be non-negative)

Pq: state covariance matrix diagonal value for mass in square kilograms (must be non-negative)

Qx: process noise covariance matrix diagonal value for x position in square meters (must be non-negative)

Qy: process noise covariance matrix diagonal value for y position in square meters (must be non-negative)

Qz: process noise covariance matrix diagonal value for z position in square meters (must be non-negative)

Qvx: process noise covariance matrix diagonal value for x velocity in meters squared / sec squared (must be non-negative)

Qvy: process noise covariance matrix diagonal value for y velocity in meters squared / sec squared (must be non-negative)

Qvz: process noise covariance matrix diagonal value for z velocity in meters squared / sec squared (must be non-negative)

Qq: process noise covariance matrix diagonal value for mass in square kilograms (must be non-negative)

v: range measurement noise covariance in square meters (must be non-negative)

fov: camera field of view (FoV) angle in degrees. Camera always assumed pointing at the CoM of the asteroid (nadir pointing). Note this is not the half angle, but the full FoV (must be positive)

segremovalth: MPC segment removal threshold in meters. This is the max distance the spacecraft can be from a reference trajectory segment for it to still be removed from contention in future MPC time steps. 

reftol: tolerance to break the SCvx reference trajectory code loop. This is the max allowable distance between corresponding points between iterations in meters (must be positive)

cost_function_to_use: a string that represents the cost function being used. It is one of the following values: fixed, terminal_free, terminal_fuel_weighted_free, progress_free, no_fuel_free, progress_ones_free

monte_carlo_bool: 0 or 1. Represents if the current MPC run is part of a Monte Carlo simulation. If 0, it uses the true state outlined above with xi through vzi. If 1, it will vary xi through vzi using the below standard deviations

monte_carlo_pos_x_sigma: 1-sigma standard deviation for varying the initial conditions for the x position in meters. The mean of this Gaussian curve is at xi

monte_carlo_pos_y_sigma: 1-sigma standard deviation for varying the initial conditions for the y position in meters. The mean of this Gaussian curve is at yi

monte_carlo_pos_z_sigma: 1-sigma standard deviation for varying the initial conditions for the z position in meters. The mean of this Gaussian curve is at zi

monte_carlo_pos_vx_sigma: 1-sigma standard deviation for varying the initial conditions for the x velocity in meters / sec. The mean of this Gaussian curve is at vxi

monte_carlo_pos_vy_sigma: 1-sigma standard deviation for varying the initial conditions for the y velocity in meters / sec. The mean of this Gaussian curve is at vyi

monte_carlo_pos_vz_sigma: 1-sigma standard deviation for varying the initial conditions for the z velocity in meters / sec. The mean of this Gaussian curve is at vzi


## Config file section - Asteroid:

asteroid: string for what asteroid the code is to be run with respect to. Can be one of the following values: bennu, kleopatra, geographos, bacchus, toutatis, castalia, golevka, itokawa

landinglocindex: index for what vertex in the shape model the user wants to be specified as the landing site. Requires overwrite_lli to be False. Must be an integer value between 0 and the number of vertices in the shape model. In the journal paper, 73 is Landing Site 1, 1832 is Landing Site 2, 227 is Landing Site 3

fnum: number of features to be randomly placed around the Landing Site (must be a positive integer)

fnum_landing_site: number of features specifically placed in a sphere around the landing site to ensure features seen doesn't decrease as the spacecraft approaches the landing site (must be a positive integer less than fnum)


## How to generate a new reference trajectory:

Within the repository, update input/config.ini to have the desired initial and final conditions or keep it the same to regenerate the same reference trajectory as seen in Figure 5 of the journal paper. Run src/SCvx.py. Figure 5 from the journal paper will generate from this script. 

## How to run a single MPC simulation:

Within the repository, update input/config.ini to have the desired initial and final conditions or keep it the same to regenerate the same MPC results as seen in Figures 6-11 of the journal paper. Run src/SCvx.py first to ensure the correct reference trajectory is being used. Once src/SCvx.py is finished, run src/MPC.py. This will generate Figures 6-11 and print out Table 4 from the journal paper. 

## How to run a Monte Carlo simulation for all cost functions and Landing Sites:

Within the repository, update all 21 config files in input/Monte_Carlo_configs to have the desired initial and final conditions or keep it the same to regenerate the same Monte Carlo results as seen in Figures 12, 13 of the journal paper. Run src/MPC_stats.py. NOTE: this script takes very long to run, typically 1-2 days. This will generate Figures 12, 13 and Tables 7-9 from the journal paper.
